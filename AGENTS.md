# AGENTS.md

Metadata repo for the YouTube channel https://www.youtube.com/@AdamSeekerOfficial. A daily GitHub Action discovers new videos and commits them to `data/videos_master.json`.

## Layout (uv workspace: SDKs, apps, later services)
- `sdks/` — reusable libraries, each its own package and wheel (names start with `seeker-sdk-`):
  - `sdks/core` (`seeker-sdk-core`): `MasterList` (load/sort/merge/save of `data/videos_master.json`, same format and `.backup` behaviour as ever), errors, settings, the plugin registry (`seeker_sdk_core.plugins`). No third-party dependencies.
  - `sdks/videos` (`seeker-sdk-videos`): video **sources as plugins** (`youtube_api`, `ytdlp` flat listing), explicit/no-fallback method resolution (`MASTER_LIST_METHOD`), `update()` / `rebuild()`, `catalog` (categorize, priority, report).
  - `sdks/transcripts` (`seeker-sdk-transcripts`): transcript **methods as plugins** (`ytdlp`, `youtube_transcript_api`), formats and conversion, `compare()`.
  - `sdks/gemini` (`seeker-sdk-gemini`): provider plugin `gemini` (google-genai, structured output with the tool's schema). Key `GEMINI_API_KEY` (`mise run local:apikey:gemini`: opens https://aistudio.google.com/apikey, checks the key with the free model-list call, header only, never printed, saves it to `fnox.local.toml`); model `SEEKER_GEMINI_MODEL` (default `gemini-flash-latest`); paced by `SEEKER_GEMINI_RPM` (default 10). **Free tier: about 20 requests a day per model** (gemini-flash-latest ran out after ~20 on 2026-10-18); other models (flash-lite, 2.5-flash, 2.5-flash-lite) have their own quota. A used-up daily quota returns Pending (exit 75, "Waiting because: ..."), never a silent switch to another model.
  - `sdks/llm` (`seeker-sdk-llm`): language-model **tools** (instructions in a versioned prompt file + JSON input + the JSON shape of the answer), **providers as plugins** (`seeker.llm_providers`: `queue` now, Gemini later), a cache per provider and model (`data/llm/cache/<provider key>/<tool>@<version>/`, e.g. `queue/`, `gemini/gemini-flash-latest/`: never pay twice, never mix models) and a per-run budget (`--max-requests`).
  - `sdks/knowledge` (`seeker-sdk-knowledge`): **processing strategies as plugins** (`seeker.processing_strategies`: `chunks` = raw captions in 3-minute windows, no model; `english-notes` = a model writes attributed English notes with times and refs per 15-minute window). Text-file store `data/knowledge/<strategy>@<version>/` (passages JSONL per video, notes markdown, manifest).
  - `sdks/chat` (`seeker-sdk-chat`): **chat strategies as plugins** (`seeker.chat_strategies`: `keyword` = BM25 with the question; `multilingual` = a model first rewrites the question into English/Roman Urdu/Devanagari/Bengali keywords). BM25 tokenizes Devanagari/Bengali/Arabic script whole (Python's `\w` would split at vowel signs). Answers cite passage ids; invented citations are dropped.
  - `sdks/eval` (`seeker-sdk-eval`): runs `eval/questions` against a (processing, chat) pair: retrieval, `must_mention` keywords, a model judge, "not found" on unanswerable; saves `data/eval/runs/` + `data/eval/latest/`, `compare` makes the table.
- `apps/` — thin front ends: `apps/cli` (`seeker-cli`, the `seeker` command) and `apps/tui` (`seeker-tui`, the menu). Apps contain no business logic.
- `services/` — reserved for deployables (a daily-update service/API later); the workspace already includes `services/*`.
- Rules: SDKs never configure logging, never `sys.exit`, never read the current directory at import; raise `seeker_sdk_core` errors instead. Apps do logging, prompts, exit codes. Dependencies point one way: apps/services -> SDKs -> core.
- Architecture, plugin groups and how to extend: `docs/architecture.md`.
- `data/videos_master.json` — master list (`videos`, `last_updated`, `total_videos`, `channel_url`). Auto-updated; also holds `.backup` copies.
- `seeker videos update | rebuild | manage`, `seeker transcripts ...`, `seeker plugins` (the CLI; normally run through mise tasks). Update needs `YOUTUBE_API_KEY` unless `MASTER_LIST_METHOD=ytdlp`.
- Transcripts (transcript download/management (`seeker transcripts` subcommands `stats`, `list-missing`, `download-missing`, `download`, `check`, `compare`). `compare` (`mise run local:transcripts:compare -- VIDEO_ID`) runs BOTH methods into `data/transcripts/compare/<id>/<method>/` (vtt + plain txt each), prints sizes/word counts and does not touch the master list. Method is explicit (`--method` or `TRANSCRIPT_METHOD`: `ytdlp` or `youtube_transcript_api`), no default and NO fallback. Two separate options: `--format` (what yt-dlp DOWNLOADS: `ttml` default, `srv1`, `srt`, `vtt`; yt-dlp only) and `--final` (the FINAL files, comma list from `srt,vtt,txt`, default `srt,txt`; `--keep-source` also keeps the download; env `TRANSCRIPT_FORMAT` / `TRANSCRIPT_FINAL`). A post-processor converts the downloaded file into the finals; with yt-dlp that is a real yt-dlp post-processor (`TextPostProcessor`, registered `before_dl`, which runs even with `skip_download`; yt-dlp's built-in `FFmpegSubtitlesConvertorPP` would need ffmpeg). Both methods download the SAME `--format`: yt-dlp natively, youtube_transcript_api by requesting the transcript's timedtext URL with `&fmt=<format>` through the library's own (proxy-aware) session, which uses the library's private `_url`/`_http_client` (guarded; revisit on library upgrades). `compare` diffs the final files of both methods (identical byte for byte on 4 videos x srt/vtt/txt, tested 2026-10-05). Files go to `data/transcripts/<id>.<final>` (git-ignored; large); the master list gets `transcript_file` (srt, else vtt, else txt) and `transcript_text_file` (txt). yt-dlp's `vtt` is YouTube's rolling-caption file (~4x bigger, repeated lines), hence ttml/srt. `seeker transcripts` logs to the console and to `logs/transcripts.log` (git-ignored; `stats` and `list-missing` only print). A finished live stream usually has only `live_chat` (the chat replay) and no captions: that is "no transcript available", not an error, and the yt-dlp `check` agrees with `download` on it. `download-missing --limit N` stops after N DOWNLOADS (videos without a transcript are skipped over; `--max-attempts`, default 50, bounds one run; 3 errors in a row stop it, since YouTube is probably blocking). A video with no transcript is remembered in the master list (`transcript_status: unavailable`, `transcript_attempts`, `transcript_checked`, `transcript_retry_after`) and looked up again after 1, 2, 4, 8 ... days (capped at 64, `retry_delay_days` in `seeker_sdk_core.masterlist`), so repeated runs move on to other videos; finding the transcript clears those notes and a rebuild keeps them. "No transcript" is a normal outcome, not an error: `download-missing` exits 1 only on real errors (blocked, network), a `download VIDEO_ID` that gets nothing exits 1. `youtube_transcript_api` maps `TranscriptsDisabled` / `NoTranscriptFound` to "no transcript" like yt-dlp does.
- `.github/workflows/update-videos.yml` — daily at 06:00 UTC, plus manual runs; no push triggers.
- `.github/workflows/rebuild-videos.yml` — manual rebuild (workflow_dispatch only). Both workflows share a concurrency group so they never push at the same time. Do not add `push:` triggers: a push that touched a script once started a real rebuild on main.
- `logs/` — script logs, committed by the workflow.
- Findings and plans on video details (flat/RSS/API sources, the 15-video RSS window, rebuild merge) and transcripts per environment: `docs/video-details-and-transcripts.md`.
- Primers for people (and agents) new to the SDKs, in `docs/primer/` (how an installed package describes itself with `METADATA` and `entry_points.txt`, plugins and entry points, the master list, YouTube sources, transcripts and caption formats; each ends with the mistakes already made and a runnable example). `scripts/tests/test_primer_docs.py` fails if a primer names a file that no longer exists, so update the primer when you move code. More primers are planned (workspace and packaging, SDK rules and errors, testing SDKs).
- Language-model work runs through **tools** and a **provider**, never a direct API call. With the `queue` provider (the default now) a command writes `data/llm/queue/pending/<id>.json` and exits **75** (waiting); a worker writes `data/llm/queue/done/<id>.json` = `{"id", "output", "worker"}` matching `output_schema` (each pending file explains this in `how_to_answer`); running the same command again validates, caches and continues. During development the workers are **disposable fast subagents** (Claude Haiku, standing in for Gemini Flash): give each a batch of pending files, ask for exactly one done file per request, then re-run the command. Rejected answers land in `data/llm/queue/rejected/` and the request stays pending. Gemini will be another provider plugin; strategies and tools do not change. Commands: `seeker knowledge strategies|process|status`, `seeker ask`, `seeker eval questions|run|compare`, `seeker llm status|pending` (mise: `local:knowledge:manage`, `local:chat:ask`, `local:eval:manage`, `local:llm:manage`; TUI group Knowledge; Tilt label `knowledge`). To change a prompt, add a new version (`english_notes_v2.md`, `version = "v2"`) rather than editing in place, so `eval compare` can show both.
- `eval/questions/` — evaluation questions for the planned processing/chat strategies (format, point of view and scoring in `eval/README.md`): one TOML file per video (file name = video id), `_cross.toml` (answers spread over videos), `_unanswerable.toml` (topics absent from `checked_against`; the right answer is "not found"). Questions are what an ex-Muslim activist or researcher would ask (which verse/hadith/tafsir, what argument, where, across videos), in English and Roman Urdu; reference answers describe what is SAID in the video, attributed, never as fact. Every `near` was read in the transcript; `scripts/tests/test_eval_questions.py` checks the format, that each reference answer passes its own `must_mention`, and (where transcripts exist locally) that `near` is inside the video and unanswerable terms are really absent. Evaluations and processing take a `--videos` filter. Record each comparison worth keeping in `eval/RESULTS.md` (date, scope, table, what it shows, caveats).
- Docs: `README.md` (yt-dlp transcripts), `README_AUTOMATION.md`, `README_REBUILD.md`.

## Conventions
- Keep `videos` sorted by `upload_date`, newest first. Both save paths sort; if you add a new write path, sort there too.
- New videos start with `status: "uncategorized"`, `auto_detected: true`, `needs_review: true`.
- The update workflow commits and notifies ONLY when the run added videos (it counts added `"video_id"` lines in the `data/videos_master.json` diff); `last_updated` bumps and log appends alone must not trigger either. Logs of quiet runs are only in the uploaded artifact.
- The update workflow keeps ONE open issue titled "📺 New Videos Available for Review" (labels `automation`, `videos`, `review-needed`) and comments on it; closing it makes the next run open a new one. Don't reintroduce one issue per run.
- Never commit a real API key; `config.env` holds placeholders only. The key comes from the `YOUTUBE_API_KEY` secret.
- `data/videos_master.json` is written with `indent=2, ensure_ascii=False`; keep that format to avoid noisy diffs.
- Update the READMEs when workflow behavior changes.

## Setup and tasks (mise + uv)
Tools and tasks are defined in `mise.toml`; the uv workspace root is `pyproject.toml` with one `uv.lock` (no requirements.txt); each package has its own `pyproject.toml`. `mise run setup` = `uv sync --all-packages`.
- `mise install` then `mise run install` — installs the tools (Python 3.12, uv, act, fnox, gh, gcloud, tilt), syncs `.venv` (`setup`), and runs `scripts/check_docker.sh`, which checks Docker (needed only for `act:` tasks) and offers to install it with Homebrew on macOS if missing.
- Secrets use fnox: declared in `fnox.toml`; put `YOUTUBE_API_KEY` in the git-ignored `fnox.local.toml` (copy `fnox.local.toml.example`), which overrides `fnox.toml`. Tasks run via `fnox exec`; in CI the key comes from the environment. Never commit `fnox.local.toml`.
- Task names are `<where>:<area>:<action>`. The first scope says where it runs:
  - `local:` runs the code directly: `local:videos:update` / `local:videos:rebuild` / `local:videos:manage <subcommand>`, `local:transcripts:manage -- <args>` (e.g. `-- --method youtube_transcript_api download-missing --limit 5`).
  - `act:` runs the workflow locally in Docker: `act:videos:update` / `act:videos:rebuild` / `act:list`. Commit, push, issue and artifact steps are skipped when `ACT` is set, so it never publishes anything.
  - `gh:` triggers the REAL workflow on GitHub and watches it: `gh:videos:update` / `gh:videos:rebuild` / `gh:list`. It really commits and creates issues. Uses the current branch (or `REF=...`); the ref must be pushed and the workflow must exist on the default branch.
  - `install` (full first-time setup), `setup` (just `uv sync --all-packages`), `test`, `menu` and `nuke` (cleanup) are unscoped (repo-wide); `build:*` and `sdk:new` are build/dev tasks.
  - `local:tilt:up` / `local:tilt:ci` / `local:workspace:graph`: the Tilt dashboard and the workspace graph (next bullet). `local:plugins:list` = `seeker plugins`.
- Tilt dashboard (`Tiltfile`, `mise run local:tilt:up`, http://localhost:10350; `TILT_PORT` changes the port): a live picture of the workspace, nothing is deployed (every resource is a local command). One resource per package in the uv workspace, read from the pyproject files by `scripts/workspace_graph.py` (`local:workspace:graph`, also `--json`/`--mermaid`), so a package added with `sdk:new` appears without editing the Tiltfile. Each package resource runs its tests, waits for the packages it depends on, and re-runs when its own code or the code of anything it depends on changes (touch `sdks/core` and every dependent lights up). Labels: `setup`, `sdks`/`apps`/`services`, `scripts`, `registry` (graph, plugins), `data` (`videos-report`, `transcripts-stats`, `transcripts-missing`, refreshed when `data/videos_master.json` changes), `methods` (`mise run all:method:show`: which method local, act and gh use; refreshes by itself when `fnox.local.toml` or `.vars` changes, and has a "Set a method (local or act)" button with a Where dropdown and one Setting = method dropdown, so an invalid combination cannot be picked), `run`/`build`/`act`/`docker`/`gh` (manual: press the trigger arrow; `transcripts-download` fetches 5 transcripts with `TRANSCRIPT_METHOD`, `tilt up -- --limit N` changes the 5). Buttons are built from Tilt's own `v1alpha1.ui_button` + `v1alpha1.cmd` (inputs reach the command as environment variables); do not use `k8s_yaml` for them (Tilt then demands a Kubernetes cluster) or the `uibutton` extension (it downloads code at run time). A button's command output goes to the `(Tiltfile)` log, so make invalid inputs impossible instead of relying on an error message. Only read-only and test resources run by themselves; anything that writes data, needs Docker or the network is manual. `gh:videos:update` / `gh:videos:rebuild` (they really commit and open issues) and `gh:method:set` (it changes the repository variable the real workflows read) are deliberately NOT buttons; `gh-runs` only lists runs and the `methods` list only reads the gh variables. `mise run local:tilt:ci` runs the automatic resources once, headless, and exits non-zero if one fails (use it to check Tiltfile changes; it uses `--port 0` so it never clashes with a running dashboard). `tilt` is disabled in the workflows (`MISE_DISABLE_TOOLS`). Resources with `resource_deps` wait for them to be green, so a failing package blocks `build-wheels`. Keep `watch_settings(ignore=...)` covering `__pycache__`, otherwise running tests re-triggers itself.
- `mise run build:sdks` builds every SDK in `sdks/` as its own wheel into `dist/sdks` (`seeker_sdk_core-0.1.0-py3-none-any.whl`, ... all starting with `seeker`; flags after `--`: `--sdist`, `--no-verify`) and verifies them: it installs the wheels (not the workspace) into throwaway venvs, checks `seeker-sdk-core` has no dependencies, that each SDK installs and imports alone, and that plugins are discovered via entry points. `mise run build:apps` does the same for the apps (`dist/apps`). `mise run sdk:new -- <name> [--plugin video_sources|transcript_methods]` scaffolds a new SDK (`sdks/<name>`, distribution `seeker-sdk-<name>`), registers it in the workspace and optionally adds a plugin skeleton.
- `mise run nuke` is the opposite of `install`: removes `.venv`, `.act/` and this project's Docker containers (label `project=adam-seeker-metadata`), their volumes, and the act runner image. Flags after `--`: `--dry-run`, `--yes`, `--all` (also uv cache, `act-toolcache` volume, this project's mise tool versions, `fnox.local.toml`). Everything act creates is predictable (see `.actrc`: label, `.act/` dirs, pinned image) so nuke can find it. Docker itself is never uninstalled. If you add new Docker/act artifacts, keep them labelled/under `.act/` and update `scripts/nuke.sh`.
- `mise run local:apikey:setup` (`scripts/api_key.sh`): guided YouTube Data API v3 key setup. gcloud is a mise tool (its installer needs Python 3.10+, hence `CLOUDSDK_PYTHON` in `mise.toml` and `scripts/ensure_gcloud.sh`). A key can only be created from the user's own Google account, so it can't be fetched automatically: it can drive gcloud after the user signs in (enable API, create a restricted key), or it opens the console pages, validates the pasted key with one API call (key sent via header, never printed), saves it to git-ignored `fnox.local.toml` (mode 600) and optionally sets the `YOUTUBE_API_KEY` GitHub secret.
- Docker lifecycle (`scripts/docker.sh`, runtime detection: Colima first, then Docker Desktop on macOS): `docker:start` starts it and waits until ready; `docker:stop` removes this project's containers/volumes then stops Colima / quits Docker Desktop (skipped if other containers are running); `docker:cleanup` removes only our leftovers; `docker:diagnose` (read-only, `scripts/docker_diagnose.sh`) compares host CPU/RAM/disk with what Docker is allocated, shows Docker disk usage, live container usage and free space in the VM, gives a verdict against act's needs (2+ CPU, 4+ GB RAM, 30+ GB disk) and prints how to change the allocation persistently for the detected runtime (Colima: `colima start --edit` / `~/.colima/default/colima.yaml`; Docker Desktop: Settings > Resources). `act:` tasks run through `docker.sh run`: they clean old leftovers first (replace, never reuse), start Docker only if it was down, always clean up afterwards (also on failure/Ctrl-C) and stop Docker only if that run started it, so nothing is orphaned.
- Method switches (two settings): `MASTER_LIST_METHOD` (`youtube_api` | `ytdlp`: how videos are discovered by `update_master.py`/`rebuild_master.py`) and `TRANSCRIPT_METHOD` (`ytdlp` | `youtube_transcript_api`: used by `transcripts.py`). Explicit means NO fallback and a non-zero exit on failure (`youtube_api` without a key also fails). `MASTER_LIST_METHOD` unset = old implicit behaviour (API if a key is present, else yt-dlp, failures only logged). Each target has its own store, set with `mise run <target>:method:set -- <master-list|transcript> <value|unset>` and shown with `<target>:method:show` (or `mise run all:method:show` for local, act and gh together): `local:` writes git-ignored `fnox.local.toml`, `act:` writes git-ignored `.vars` (act reads it as `vars.*`), `gh:` sets a REPOSITORY VARIABLE (`gh variable set`) that the workflows read as `vars.MASTER_LIST_METHOD`. No workflow uses `TRANSCRIPT_METHOD` yet. Scripts: `scripts/method.sh`.
- `mise run menu` (`apps/tui`, Textual): terminal UI to pick where to run (local/act/gh), what to run and its options instead of remembering task names. It lists actions in groups (Videos, Transcripts, Methods, Setup, Docker, Dashboard, Knowledge, Develop, Danger); method, provider and strategy choices come from the plugin registry (`seeker-tui` depends on `seeker-sdk-core` for that), and the transcript method defaults to the saved `TRANSCRIPT_METHOD`, shows the exact `mise run ...` command live, asks for confirmation for anything that publishes (gh) or is heavy (rebuild, nuke without `--dry-run`), and runs the command in the real terminal (so prompts like API key setup work). Actions are data (`ACTIONS` in `apps/tui/src/seeker_tui/app.py`). **The menu must stay in sync with the CLI and mise:** `scripts/tests/test_tui_cli_parity.py` runs every action through every combination of its fields, turns each `mise run <task> -- args` it builds into the real `seeker` command via `mise.toml`, and parses it with the real CLI parser. It fails if the menu builds a command the CLI rejects, or if any CLI command, CLI option or mise task cannot be reached and is not in `CLI_EXCEPTIONS` / `TASK_EXCEPTIONS` with a reason (an exception that is no longer needed fails too). So when you add a CLI command or option or a mise task, add it to the menu, or add an exception that says why not. Tests: `mise run test` runs every package's tests (SDKs, CLI, and the TUI flows headless).
- Workflows call the `local:` tasks, so local, act and GitHub run the same commands. Test order: `local:` then `act:` then `gh:`.
- After changing dependencies run `uv lock` and commit `uv.lock`.
